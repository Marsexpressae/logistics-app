# Sales rep (customer owner) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every customer has an owner (the sales rep) and every booking carries the rep who made that sale; both are chosen from active staff, changeable only with a new permission, and shown on the main screens.

**Architecture:** Four new columns (`sales_rep_id`, `sales_rep_name` on `customers` and on `bookings`), a trigger that copies the name and checks the person, a permission-checked update rule, one choices function, and the owner copied onto customers created from bookings. The three database functions behind the Accounts list, the global search and the customer search gain the new field. The sample-data layer mirrors all of it. One shared dropdown component serves the booking form, the booking page and the customer page.

**Tech Stack:** Next.js 16 App Router, React 19, Tailwind v4, Supabase Postgres (RLS, `has_perm`, `require_perm`), node:test with the sample-data mock (`npm test`) and real-database tests (`npm run test:db`).

**Spec:** `docs/superpowers/specs/2026-10-18-sales-rep-design.md`

## Global Constraints

- Migration file: `supabase/migrations/0061_sales_rep.sql`. Additive and re-runnable (`add column if not exists`, `create or replace`, `drop trigger if exists`, `on conflict do nothing`).
- Columns: `customers.sales_rep_id uuid references profiles(id) on delete set null`, `customers.sales_rep_name text`, `bookings.sales_rep_id uuid references profiles(id) on delete set null`, `bookings.sales_rep_name text`; an index on each `sales_rep_id`. Existing rows stay null.
- Name trigger: `before insert or update of sales_rep_id` on both tables; function `set_sales_rep_name()`, `security definer`, `set search_path = public`: when `sales_rep_id` is null set the name to null; otherwise the id must belong to an **active** profile (`That person is not active staff`) and the name is copied from `profiles.full_name`.
- Update rule: trigger `before update of sales_rep_id` on both tables (function `require_sales_rep_permission()`): when the id changes and `has_perm('sales_rep.change')` is false, raise `Only managers can change the sales rep`. Insert needs no extra permission.
- Permission `sales_rep.change`, label `Change the sales rep (owner)`, group `Customers`, description `Choose or change who owns a customer and who made a booking`; granted to `manager` and `super_admin` only (`on conflict do nothing`).
- `sales_rep_choices() returns jsonb` (`[{ "id", "name" }]`, active profiles ordered by `full_name`): `security definer`, `set search_path = public`; allowed when `has_perm` is true for any of `bookings.create`, `customers.edit`, `sales_rep.change`, otherwise raise the standard `You do not have permission to do this` with errcode `42501`; `execute` revoked from `public, anon`, granted to `authenticated`.
- Owner on new customers: `booking_ensure_customer` (migration 0044) and `create_customer_from_booking` (0039) copy the booking's `sales_rep_id` into the customer they create; `create_customer` (0039/0041) sets the owner to `auth.uid()`; a customer found by phone is not changed; updating a customer's owner never touches that customer's bookings.
- Replace with the **live** definitions (read each with `select pg_get_functiondef('<name>'::regproc)` through `db:migrate`'s connection, as migration 0055 did), changing only the new field and keeping signatures and grants: `accounts_invoices` (new output column `r_sales_rep text` = the booking's rep name), `global_search` (each booking hit gets `sales_rep`, each customer hit gets `sales_rep` = the owner's name), `search_customers` (each customer gets `sales_rep_id` and `sales_rep`).
- Types: `Booking` gains `sales_rep_id?: string | null; sales_rep_name?: string | null`; `Customer` and `CustomerHit` gain the same two fields (`CustomerHit` as `sales_rep_id`, `sales_rep`).
- UI text (exact): list column and labels `Sales rep`; on customer screens `Owner`; empty value `—`; the empty choice `No sales rep`; save note `Saved`. Dropdowns are full width with the standard 44px touch size (`inputClass`).
- Not shown on: printed receipts, credit notes, refund receipts, the return form, statements, the public tracking page. The assigned driver stays everywhere it is today.
- Sample-data storage key `logistics-mock-db-v37` becomes `logistics-mock-db-v38`.
- Git: commit as `ibnhabib <shoaib.amir@hotmail.com>`; no Claude co-author line; no push or deploy without the owner's explicit word; a migration changes the LIVE database, so tell the owner, take `npm run db:backup`, wait for "apply".

## Review Focus

1. A person without `sales_rep.change` cannot change the rep of a customer or of a booking, but can set it when creating; a manager can change both (Task 1).
2. An inactive person, an unknown id and a removed person's old records: refused or kept with the old name (Task 1).
3. A booking for a new customer makes the customer's owner the same person; a booking for an existing customer leaves the owner alone; a customer added by hand gets its creator (Task 2).
4. Changing a customer's owner never changes that customer's old bookings (Task 2).
5. The Accounts list, global search and customer search return exactly what they returned before, plus the new field, for people with and without rights (Task 3).
